## Reproduction and diagnosis

[Instrumented baseline run 38099353203](https://github.com/avahgard/moneyszn/actions/runs/38099353203)
at `d0607962a69c579e7a8def5ab70e442aaad04fff` reproduced the original signature:

| Configuration                 | Startup cases | Update cases        | Total                |
| ----------------------------- | ------------- | ------------------- | -------------------- |
| Serial, job 114351867764      | 10 passed     | 8 passed / 2 failed | 18 passed / 2 failed |
| Two workers, job 114351867905 | 10 passed     | 4 passed / 6 failed | 14 passed / 6 failed |

The ordinary uninstrumented [required run 38099353075](https://github.com/avahgard/moneyszn/actions/runs/38099353075)
also failed the same WebKit assertion (15/16 passed). Instrumentation is therefore
not necessary for the failure. Parallelism is not necessary either; these small
samples do not establish a reliable failure-rate difference.

Every instrumented failure shows fixture B, a complete visible document, a
controlled page, register settlement within 15-24 ms, no installing/waiting
worker, and both controller and registration.active remaining `activating`
through ten seconds. No page errors were observed. The replacement document
never reaches registration.update(): it is awaiting waitForShellActivation().
Neither slow register settlement nor the post-readiness update promise explains
the stall. pageshow occurs normally; no further controllerchange repairs it.

Example from serial job 114351867764, origin port 39345: revisit document
`1791679451364-0.7680080484104871` sees update start at 16 ms, settlement at 29 ms,
installing at 30 ms, activating/controllerchange at 41 ms, and activated at
47 ms. The immediate reload's document `1791679451413-0.06038467862928676` starts
with an activating controller, settles register at 21 ms, and repeated independent
getRegistration() calls still expose activating at 3, 4 and subsequent seconds.
The predecessor saw activation complete while the new document retained an
earlier state. Thus this is an observed WebKit document-state propagation race,
not proof that the underlying worker's activate handler is still running.

**Conclusion:** an application lifecycle assumption exposes a WebKit-specific
reload/activation race (A with C interaction), not an invalid readiness assertion
(B). The application reloads at controllerchange even when the new controller is
still activating. The [Service Worker activation algorithm](https://www.w3.org/TR/service-workers/#activation-algorithm)
allows controller notification before activation completes; controller existence
is not completion evidence. Confidence is high in the observed sequence and
failure locus, with browser-internal causation unproven. No WebKit engine bug
identifier is claimed.

## Correction

Wait for the actual replacement controller to reach activated before the existing
takeover reload. Subscribe before inspecting its state, remove stale observers,
ignore redundant/superseded controllers and reload at most once. Initial claiming
still does not reload. Readiness continues to require an activated shell; no
polling, retries, timeout inflation or weaker readiness criterion is introduced.
Worker precaching, activation cleanup and fetch behavior remain unchanged.

Five unit regressions cover activation order, already-activated takeover, first
installation, redundant replacement and supersession. Two real-browser scenarios
hold activate.waitUntil after clients.claim using a test-only HTTP gate and
interrupt replacement precaching with HTTP 503. They verify delayed takeover,
old-shell offline recovery, successful retry and fixture-B offline restart.
The held activation/503 scenarios are controlled fault simulations, separately
from the ordinary deployment test reproducing the real CI symptom.

That additional failure revealed an invalid **new test** assumption: Playwright's
context offline setting alone does not cut Firefox's worker-side network fetch.
The trace shows offline HTML B returning 200 and its B module failing offline,
not loss of the cached A shell. The proxy now also closes the network transport
during the offline sections, forcing the real worker's network-first fallback.
This preserves the old-shell and new-shell assertions. Both new Firefox fault
scenarios then passed locally with the fresh runtime. Production code was not
changed to address this emulation issue. This separate test-harness correction
does not reclassify the original CI-01 failure as a test race.

An isolated negative probe built application source from accepted `084da18` and
ran the held-activation case: it failed by timeout during the premature navigation
while the activation gate remained held; cleanup then encountered a closed
context. This is supporting regression evidence, not a repeat of the original
WebKit symptom. The first isolated probe had a server cwd setup error, corrected
before this negative run. A preliminary message-based activation gate also timed
out in Chromium; it was replaced by the HTTP gate because message delivery can
wait for activation. These failed probes are not claimed as PASS results.
